## 3. 今日完成的工作

### 3.1 ZK1 复验（回归确认）

ZK1 维持 `exit=0`，本次未做任何改动，确认新改动未污染 ZK1 路径。

### 3.2 修复 A：guest 启用 `heap-embedded-alloc`（宿主机内存暴涨 → 平台期）

现象：修 ZK2 期间观察到 r0vm（宿主机）RSS 持续增长直至 OOM。
原因：guest 侧默认堆分配器不回收；risc0 提供 `heap-embedded-alloc`（内嵌 TLSF/rlsf 分配器）后可回收。
修复：在 ZK2 guest 的 `risc0-zkvm` 依赖特性中加入 `heap-embedded-alloc`
（`zkFHE-Decryption-Proof/decryption-proof/methods/guest/Cargo.toml` 现为
`features = ['std', 'heap-embedded-alloc']`，该改动由 `tools/env_setup.sh` 用 `sed` 幂等落实）。
配套：risc0 依赖的 `embedded-alloc 0.6.0` 使用旧 API `Layout::dangling`，与本机 rustc 不兼容，
故通过 `[patch.crates-io]` 指向 `zkFHE-Decryption-Proof/vendor/embedded-alloc-0.6.0`（同版本 + 2 行改名补丁），
同样由 `tools/env_setup.sh` 内置完成。

效果（实测）：r0vm 内存从「无上限增长」变为在 **≈184MB** 处形成平台期（本轮采样 `rss=193MB` 稳定不涨）。
注意：**该特性只让堆可回收，不会抬高 192MiB 的 guest 地址空间上限**（见 §4.1）。

### 3.3 修复 B：guest 输入处理改为「读一个 → 立即反序列化 → 立即释放」

原实现：先把 7 个输入全部 `env::read()` 进常驻 `Vec<u8>`（≈114MB：`std_bootstrapping_key`≈50MB + `fourier_bsk`≈64MB），
再逐个反序列化 → 峰值 ≈210MB > guest 192MiB 上限 → guest 侧 `memory allocation of ... failed` → guest abort
→ 宿主机表现为 `Trap: IllegalInstruction(c0001073)`。

重写 `zkFHE-Decryption-Proof/decryption-proof/methods/guest/src/main.rs`：
按「读一个 → 就地反序列化 → 立即 drop」顺序处理，仅保留真正参与计算的三份数据
（`pbs_multiplication_ct`、`big_lwe_sk`、`cleartext_multiplication_result`）。

guest 侧的输入读取顺序**必须与 host 的 `.write()` 顺序严格一致**，当前为：

| 次序 | 输入 | 体量 | guest 用途 |
| --- | --- | --- | --- |
| 1 | `std_bootstrapping_key` | ≈50MB（≈6.19M × u64） | 仅反序列化校验，随后释放 |
| 2 | `fourier_bsk` | ≈64MB（≈4.19M × c64） | 仅反序列化校验，随后释放 |
| 3 | `lwe_ciphertext_in_clear` | 小 | 仅反序列化校验，随后释放 |
| 4 | `cleartext_multiplication_result` | 小 | **保留**，用于 `assert_eq!` |
| 5 | `accumulator` | 小 | 仅反序列化校验，随后释放 |
| 6 | `pbs_multiplication_ct` | 小 | **保留**，解密 + `commit` |
| 7 | `big_lwe_sk` | 小 | **保留**，解密用 |

重写后的写法（当前 `main.rs` 的形态，示意）：

```rust
// 1) std_bootstrapping_key（≈50MB）：校验 PBS 的 bootstrap key 能传入并在 zkVM 内反序列化
{
    let serialized_std_bootstrapping_key: Vec<u8> = env::read();
    let _std_bootstrapping_key: LweBootstrapKeyOwned<u64> =
        deserialize_with_context(&serialized_std_bootstrapping_key, "std_bootstrapping_key");
}   // 作用域结束 → 输入字节 + 结构体一并释放
// 2) fourier_bsk 同理；4)/6)/7) 需要保留的值则绑定到外层变量并显式 drop 输入字节
```

效果：峰值从 ≈210MB 降到预计 ≈161MB，**推进了执行位置**（bsk 输入整体读取成功，见 §4.3），但仍在下一步分配失败。

## 4. 关键事实与实测数据

### 4.1 guest 地址空间上限（本次核实）

- `risc0-zkvm-platform-1.2.6/src/memory.rs`：`GUEST_MAX_MEM = SYSTEM.start = 0x0C00_0000` = **192MiB**（硬上限）。
- guest ELF 的 `_end = 0x0032_1b03`（≈3.13MB），堆从 `_end` 到 192MiB 上限 → 堆空间 ≈**189MiB**。
- 结论：**堆容量本身不是瓶颈**；失败必然是「失败那一刻已被占用」导致。

### 4.2 内存探针结果（启动后、任何输入读取之前）

`64MiB` / `96MiB` / `150MiB` 连续块申请**全部成功** → 排除「分配器尺寸类上限 / 无法分配大块」类假设
（此前曾怀疑 rlsf `Tlsf<usize, usize, {usize::BITS}, {usize::BITS}>` 的最大块限制，已被证伪）。

### 4.3 崩溃点证据（最新一轮，guest 日志 + cycle 计数）

```
R0VM[280]          ZK2G: guest start
R0VM[23069383]     ZK2G: probe 64MiB = OK
R0VM[57673067]     ZK2G: probe 96MiB = OK
R0VM[111740915]    ZK2G: probe 150MiB = OK
R0VM[111741177]    ZK2G: probe done
R0VM[111741194]    ZK2G: step1 read bsk          <-- 读 bsk 输入开始
R0VM[4002885160]   ZK2G: step1 deserialize bsk   <-- 读取成功（消耗 ≈38.9 亿 cycle）
memory allocation of 67108864 bytes failed      <-- 64 MiB 分配失败（guest abort）
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace
```

宿主机侧：

```
thread 'main' (190841) panicked at host/src/main.rs:244:10:
called `Result::unwrap()` on an `Err` value: Trap: IllegalInstruction(c0001073), pc: 0x000c2c23(0x0030b08c)
```

其它采样：`r0vm_cpu ≈ 00:04:50`、`rss=193MB`（平台期）、`logbytes=312,213,196`。

判读要点：

1. **`pc` 变化 + `step1 read bsk` 标记出现** → 说明 guest 确实被重新编译、修复 B 生效（旧行为下根本走不到这一步之后的标记）。
2. 失败请求**恰好又是 64MiB（2^26）**，与旧实现的失败尺寸完全一致，但**发生位置前移**：从「7 个输入全读完后的第一次反序列化」前移到「第 1 个输入（bsk）的反序列化」。
3. bsk 输入读取单独消耗 **≈38.9 亿 cycle**，说明 risc0 serde 的输入流是「逐元素 word 编码」（每个 `u8` 以 1 个 32-bit word 传输），
   实际流大小约为数据的 4 倍（bsk 约 198MB 流），这也解释了读取为何要数分钟。

### 4.4 代码事实（risc0 1.2.6，用于后续定位）

- `risc0-zkvm/src/serde/deserializer.rs`
  - `deserialize_bytes`：先读长度，再 `vec![0u8; len_bytes]`（**单次精确分配**，无倍增），随后 `read_padded_bytes` 填充。
  - `deserialize_str`：同样 `vec![0u8; len_bytes]`。
  - `SeqAccess`（`Vec<T>` 走 `deserialize_seq` → `visit_seq`）：**按元素逐个 `next_element_seed`**，
    `size_hint = 剩余 len` → 目标 `Vec` 会走**容量倍增**路径（本例 bsk 的 `Vec` 最终容量 64MiB）。
  - ⚠️ 待查：`visit_seq` 路径下是否存在按整段 seq 分配的临时缓冲（或 `take_words` 之类的泄漏式零拷贝缓存）。
    这是当前唯一未被排除的「隐藏大分配」来源。
- `risc0-zkvm/src/guest/env/mod.rs` / `env/read.rs`：`env::read` 通过 fd reader 走 syscall 读入。
- `risc0-zkvm-platform-1.2.6/src/heap/embedded.rs`：`HEAP.init(_end, GUEST_MAX_MEM - _end)`。

## 5. 未解决问题（当前卡点）

### 5.1 现象

在 `step1 deserialize bsk` 处申请 64MiB 失败。按当前模型估算，此刻活跃内存应约为：

| 项 | 估算 |
| --- | --- |
| bsk 输入 `Vec<u8>`（49.1MB 数据 → 倍增后容量 64MiB） | ≈64MiB |
| 反序列化目标 `Vec`（由 33.5MiB 倍增到 64MiB） | 33.5MiB（+ 64MiB 本次请求） |
| **合计峰值** | **≈161.5MiB < 189MiB 堆** |

也就是说：**理论上应该能过，实际却失败** → 说明存在一个尚未识别的、规模 ≥28MB 的额外占用（或堆碎片/未回收）。

### 5.2 已排除的假设

| 假设 | 证伪依据 |
| --- | --- |
| 分配器最大块限制（TLSF/rlsf 尺寸类） | 启动探针 150MiB 连续块成功 |
| guest 堆容量不足 | 堆 ≈189MiB，探针已证 |
| 宿主机内存不足 / OOM | r0vm RSS 稳定 193MB 平台期 |
| 修复 B 未生效（构建缓存导致跑旧 ELF） | `pc` 变化 + `step1 read bsk` 标记出现 |
| 输入根本没被 reader 读到（IO 语义错） | `step1 deserialize bsk` 标记出现，说明 read 已成功返回 |

### 5.3 待验证（下一步，逐项）

1. 在 guest 中记录 **输入 `Vec<u8>` 的 `len()` 与 `capacity()`**（`ZK2G: step1 in-bytes=… cap=…`）。
2. 记录 **bincode 头部声明的元素个数**（bincode 1.x 默认 fixint，前 8 字节即 `Vec` 元素数）及其 ×8 的期望字节数，
   用来判断 guest 眼中的 bsk 规模是否与预期（≈6.14M × u64 ≈49MB）一致。
3. 在**反序列化之前**插入「最大可分配连续块」探针（阶梯/二分 `try_reserve_exact`，输出 `ZK2G: step1 max-block=…MiB`）：
   若报出的最大块 < 64MiB，则确证「已占用远超估算」；若 ≥64MiB，则问题在分配器/请求形态而非剩余容量。
4. 审查 `risc0-zkvm/src/serde/deserializer.rs` 的 `visit_seq` / `deserialize_seq` 全路径，
   确认是否存在与 seq 长度成正比的临时缓冲，或 `Vec::leak`/`Box::leak` 式零拷贝缓存（§4.4 的“待查”项）。

## 6. 建议的最终修复方向（待与用户确认后再动手）

按「代价从小到大」排列：

1. **流式/惰性反序列化**（若 §5.3 证实输入 `Vec` 与目标结构在同一时刻共存）：
   让 guest 直接从 reader 反序列化（`bincode::deserialize_from(reader)` 风格），避免「输入字节 + 目标结构」双份共存。
2. **两个大而未被使用的输入改为「只校验长度、不物化结构」**：
   `std_bootstrapping_key`、`fourier_bsk` 在 guest 中只是被接收、从不参与计算；
   guest 仍完整读取其字节并校验长度/形状，但不构造大结构体。
   优点：不改 host 的输入条数（仍是 7 写 7 读，§3.4 自检项 8 仍成立），峰值直接降到「单个输入 `Vec`」级别；
   且**所有输入仍被绑进 input digest**（密码学上的绑定性质不丢失）。
3. **减小输入体积**（改 host 侧）：例如只把 guest 真正需要的三份数据送进 guest。
   代价：改变了 demo 的「交付全量 PBS 工件」语义，需要同步改文档与自检项。
4. 若最终必须保留全量物化：考虑「分块/分次执行」或换用更大地址空间的执行配置（改动最大，暂不推荐）。
